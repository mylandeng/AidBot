## 推荐开发阶段

### 阶段 0：项目脚手架与接口合同
- 目标：为后端、前端、数据库和本地开发建立可运行基线。
- 交付物：`backend/`、`frontend/`、`docker-compose.yml`、环境变量示例、共享 API/数据合同草案。
- 验收标准：后端健康检查接口可用；前端基础页面可加载；数据库可启动；存在一条命令启动本地栈，或有清晰的本地启动文档。

### 阶段 1：认证与最小工作台
- 目标：用户可以登录，并进入受保护的内部工作台。
- 交付物：用户/角色表、登录 API、token/session 处理、前端受保护路由、基础布局。
- 验收标准：有效用户可以登录；无效用户会被拒绝；未登录用户不能访问受保护页面。

### 阶段 2：不含完整 RAG 的问答 MVP
- 目标：在引入知识入库复杂度之前，先建立核心问答链路和持久化能力。
- 交付物：会话/消息表、聊天 API、LLM provider 抽象、聊天 UI、回答持久化、占位来源引用合同。
- 验收标准：用户可以提问并获得回答；会话历史可以持久化；即使来源为空或为占位数据，API 响应也已包含最终的引用来源结构。

### 阶段 3：手动知识库与基础 RAG
- 目标：让回答可以追溯到上传或手动录入的知识。
- 交付物：知识源/文档/chunk 表、上传或手动 FAQ 录入、文档解析与切片、embedding、向量检索、来源引用。
- 验收标准：上传或手动录入的知识可以被检索；聊天接口返回相关来源引用；检索结果经过用户可见范围过滤。

### 阶段 4：反馈采集与管理员复盘队列
- 目标：用每条回答评分和管理员处理闭合 MVP 质量反馈链路。
- 交付物：回答反馈 API/UI、反馈标签/备注、管理员队列、状态流转、按产品线/状态的基础筛选。
- 验收标准：每条回答都可以评分；低分反馈会进入管理员队列；管理员可以附备注并标记 `pending/processing/resolved/ignored`。

### 阶段 5：知识运维与可审计性
- 目标：给管理员足够的运营控制能力，用于维护 MVP 知识质量。
- 交付物：知识列表/状态页、即使是本地上传也有同步/任务状态模型、检索日志、关键动作审计日志。
- 验收标准：管理员可以查看知识项和入库状态；入库失败可见；一次聊天回答可以追溯到 message、retrieval log、source chunk 和 feedback。

### 阶段 6：MVP 加固与发布门槛
- 目标：让 MVP 达到内部试点可用的稳定度。
- 交付物：smoke tests、核心流程 API 测试、种子数据、错误处理、部署说明、权限/密钥/日志安全审查。
- 验收标准：干净本地环境可以成功启动；auth/chat/RAG/feedback/admin 核心 smoke 流程通过；日志不输出密钥；权限过滤在服务端强制执行。

## MVP 最短路径
阶段 0 -> 阶段 1 -> 带占位来源的阶段 2 -> 带最小手动/上传 RAG 的阶段 3 -> 阶段 4 反馈采集/管理员队列 -> 阶段 6 加固。

除非内部试点前就把运营追溯性列为强需求，否则阶段 5 可以放在阶段 4 之后推进。
