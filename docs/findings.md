# AidBot MVP 架构审阅发现

## 当前项目状态
- 当前类似仓库的目录包含 `AGENTS.md`、`CLAUDE.md`、`docs/mvp-architecture.md` 和 `graphify-out/`。
- 目前还没有应用代码脚手架。
- Graphify 将 `docs/mvp-architecture.md` 识别为中心来源，核心枢纽包括 MVP 架构、模块清单和后续扩展边界。

## 架构文档摘要
- 目标用户群体：公司内部售后、客服、技术支持和产品支持人员。
- MVP 目标：登录、提问、追溯来源、回答评分，并允许管理员复盘反馈。
- 建议技术栈：Next.js/React 前端、FastAPI 后端、关系型数据库、文件/对象存储、向量库、OpenAI-compatible LLM gateway。
- 明确非目标：外部客户门户、多租户 SaaS、复杂工作流审批、MVP 阶段的飞书/MCP 实时同步。

## 初步审阅发现
- 架构具备清晰的 MVP 边界，并正确延后了 MCP/飞书和平台化能力。
- 原文提出的 Phase 1 同时包含登录、聊天、历史和管理后台，作为第一个可验收切片过大。
- RAG 被列为 Phase 2，但 MVP 定义又要求来源可追溯；因此初始聊天切片至少需要占位引用合同，或一个简单的手动知识源。
- 权限过滤被正确标记为后端职责，但在实现前需要先明确数据模型和接口合同。
- 反馈是业务闭环的核心，但应先从“每条回答评分采集”开始，再扩展到管理员分诊工作流。

## 架构审阅
- 优点：产品闭环清晰，即认证 -> 提问 -> 带来源回答 -> 评分 -> 管理员复盘 -> 改进知识。
- 优点：MVP 排除项合理；延后飞书/MCP、多租户 SaaS、数据大屏、Prompt A/B 平台和自动知识改写，可以降低早期风险。
- 风险：当前文档定义了很多模块，但缺少 API 合同、数据约束和权限强制测试。
- 风险：`PostgreSQL / MVP 可 SQLite` 需要在实现前决策。SQLite 更适合快速 demo；如果很快需要向量扩展、认证和审计，PostgreSQL 更稳。
- 风险：“RAG MVP 内置在 FastAPI”可以接受，但 retrieval、embedding 和 parsing 应该放在服务接口背后，避免后续拆分时重写聊天/业务 API。
- 风险：管理员能力容易膨胀。MVP 的后台界面应聚焦反馈队列、知识状态和试点运行必要的系统设置。

## 推荐决策
- 如果 Docker 可接受，建议从一开始使用 PostgreSQL；否则 SQLite 只用于最初脚手架，但 repository/service 边界保持数据库无关。
- 从阶段 2 开始，就把来源引用视为 chat API 合同的一部分，即使完整 RAG 尚未完成。
- 权限范围先采用角色/产品线维度，不要一开始就做复杂的文档级 ACL。
- 将反馈采集纳入 MVP，但把高分答案池、评测样本生成和 Prompt 调优工作流延后到内部试点之后。
